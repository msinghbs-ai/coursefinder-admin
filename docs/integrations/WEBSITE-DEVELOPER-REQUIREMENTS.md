## Rules for any change the website reads

1. **Additive only.** `website-search-v2` keeps every field, filter and action it has. New fields and filters are added; nothing is renamed or removed. A breaking change needs a new contract (Version 3) and a Platform Admin decision.
   **Versions (Decision 277, Platform Admin 12 Nov 2026 21:00):** Website API v2 is frozen (G3): nothing is added to it either. New work goes into **Website API v3** (`website-search-v3`, `public.website_v3_*`), a separate copy of v2 reading the same data with the same keys. v3 takes additions freely until the website goes live on it; at go-live the Platform Admin records the date and v3 joins the frozen surface in the same change. Each request below says which version returns it.
2. **The provider Published switch is the control.** A provider switched off or archived is not returned by any action, with its courses, campuses and scholarships (`security.provider_hidden_v1`).
3. **Nothing is inferred.** null means not held. No defaults, no estimates, no currency conversion.
4. **Guard and record.** Every replaced website function is md5-guarded in its migration. `tests/uat/cf-247-website-api-v2-contract.spec.mjs` and `cf-247-institution-type-contract.spec.mjs` must pass.
5. **Reissue the developer pack** for any change the developer can see: edit the guide master, add a line to its section 13 (Changes to this guide), update `gen_api.py` if a field, filter or action changed, run `build.sh`, and check every example live. Update this register and System reference §4b in the same entry.
6. Keep repository names, commit hashes, internal tools and keys out of the developer pack. Keys go to the developer by a secure channel only.

## How requests are taken in and reported (Platform Admin, 12 Nov 2026)

1. **Intake.** Any new ask from a developer (email, WhatsApp, PDF, call note) gets the next ID here (R for website, Z for Zoho) in the same week, with who asked, the date and the source. One ask per row; a repeat ask is a dated note on the existing row.
2. **Triage status**, one of: *Delivered* (field and name), *Partly delivered*, *Queued for API v3*, *Decision needed (D-n)*, *Data work* (no API change until held), *Answer only*, *Declined* (with reason). Consumer-visible changes go to API v3 (Decision 277) and are held for developer comms before release.
3. **Confirmed back.** When the Platform Admin confirms a field or value to a developer, note the date on the row. What was promised is what is tracked.
4. **Weekly check (Monday morning, Melbourne).** A scheduled task reads new developer emails, proposes new rows, re-checks open rows against live functions and data, and drafts a status email per developer as a Gmail draft. Nothing is sent and nothing is merged by the task; the Platform Admin reviews, sends and approves.
5. **Status to developers** is written from this page only: delivered since last update, queued for v3, needs your input, not held. No repository, commit or internal tool names; keys only by a secure channel.
6. The working sheet (claude.ai "StudySearch Requirements Register") is a view of this page and is refreshed from it, not the other way round.

## Intake start-date status (R28, for the developer handover; approved 12 Nov 2026, Website API v3 only)

`start_date` is null unless the exact first teaching day is proved by the university's own approved academic calendar (or a dated line on the course page). In Website API v3, `start_date_status` says why it is null (v2 does not return it). One value per intake, always one of these:

| `start_date_status` | Meaning for the website | Where the gap is | Show to visitors | Australia, live 12 Nov 2026 21:2x (active intakes, 24,227) |
|---|---|---|---|---|
| `known` | `start_date` holds the first teaching day | — | the date | 4,319 |
| `no_official_calendar` | The university's official academic calendar for that year is not held or not approved | Academic calendar | the month (and year if held); "exact date to be confirmed" | 10,137 |
| `month_only` | The course page gives a month (e.g. "February"), but no study period or date, and the university is not yet approved for the nearest-start rule | Course page gives only a month | the month | 2,887 |
| `not_on_course_page` | The course page does not state this intake as an offering (or only in a past year or a student's story) | Course page | the month; treat the intake as unconfirmed | 32 |
| `course_page_not_verified` | The page read for this course is not proved to be this course's own page | Course page identity | the month | 3,144 |
| `next_year_calendar_pending` | This year's start has passed and the next year's calendar is not yet published or read | Academic calendar (next year) | the month; "dates for next year to be confirmed" | 1,490 |
| `not_yet_read` | The page wording has not been read yet (the AI or reader has not fetched or kept it) | Not fetched / not read | the month | 819 |
| `own_calendar` | Vocational, pathway or research course that follows its own calendar, not the main teaching calendar | Different calendar | the month | 230 |
| `conflicting_evidence` | The page or calendar gives more than one possible start (several dates, several periods, a period that starts in another month) | Evidence disagrees | the month | 1,078 |
| `held_for_review` | A person withdrew or locked the value; waiting for review | Review | the month | 91 |
| `rolling` | Rolling or flexible intake: no fixed start | — | "start any time" | 0 measured |

Rules for the website (when approved): never invent a date from the month; show `start_date` only when `start_date_status` = `known`; the list is closed (a new value would be an API change under section 13). Deadlines follow the same idea later (`application_deadline` is held on 38 Australian courses today).

How each value is worked out (platform side, no API change): `known` when `course_intakes.start_date` is set; otherwise from the intake's `pipeline.course_intake_dates` row — `next_action` `calendar_needs_correction` or `awaiting_official_calendar`, or no row at a university with no approved calendar → `no_official_calendar`; `waiting_for_next_academic_year` → `next_year_calendar_pending` (or `not_on_course_page` when the reason says the page does not state the month); `course_identity_unresolved` → `course_page_not_verified`; `reader_correction_needed`, or no row at a university with a calendar → `not_yet_read`; reason "names no study period" → `month_only`; reason "vocational or pathway" or "research degree" → `own_calendar`; `human_decision_required` → `held_for_review`; rolling wording → `rolling`; anything else → `conflicting_evidence`.
