StudySearch — Make Autonomous Recovery Learn From Outcomes

Continue the current Integration Controller development. Do not restart the existing three workstreams.

Platform Admin direction: Claude must stop being the routine operational troubleshooter. StudySearch must increasingly diagnose and recover known failures using its own evidence, verified remedy history and authorised platform controls.

1. Verify the actual autonomy level

For the last 24 hours, separate outcomes into:

- Detected automatically.
- Diagnosed automatically.
- Remedied automatically.
- Verified automatically.
- Required Claude engineering.
- Required Platform Admin authority.
- Required a human Layer 4 decision.

Show counts and actual admitted/published results.

Do not classify Claude-developed fixes as independently discovered platform remedies.

2. Build on the existing AI Operations Controller

Extend the existing root-cause, issue-fingerprint and work-continuity mechanisms with a reusable recovery knowledge base.

Each verified remedy should retain:

- Failure fingerprint and root cause.
- Evidence and conditions that triggered it.
- Remedy performed.
- Authority required.
- Expected outcome.
- Observed outcome.
- Success or failure.
- When the remedy must not be retried.
- Conditions that permit future automatic reuse.

Prefer existing database objects and contracts. Do not introduce a competing AI controller.

3. Make operational learning actionable

When the same failure recurs:

1. Identify the matching verified remedy.
2. Confirm the current evidence and prerequisites match.
3. Apply the remedy only if already authorised.
4. Verify actual stage advancement.
5. Record effectiveness and cost.
6. Park or escalate if the remedy cannot succeed.

A remedy that repeatedly produces no useful result must lose automatic retry eligibility.

Higher-reasoning AI may diagnose unfamiliar cases within existing approved limits, but cannot independently change admission policy, production code, spending ceilings or protected data.

Unfamiliar code defects become owned engineering work with evidence rather than silently repeated jobs.

4. Apply this to AER and Course Links first

For AER, stop deterministic re-reads against unchanged evidence, reader and settings. Automatically reconsider only when the missing condition changes.

For Course Links, learn which previously approved identity and source-validation rules consistently settle eligible cases. Reuse only those rules already authorised for the relevant scope.

Keep new policy proposals separate from existing authority.

For unresolved source problems, automatically prepare the correct Human input needed intervention.

5. Correct Layer 4 classification reporting

Reconcile the 4,430 pending items against the 5,410 summed group counts.

Ensure one primary disposition per item, with separate secondary reasons.

Report genuine admissions, technical recovery, reroutes, duplicates, supersessions and publication separately.

6. Demonstrate closed-loop autonomous recovery

Select representative previously failing cases from AER, Course Links and scholarships.

Prove:

- The platform recognises the recurring root cause.
- It selects a previously verified authorised remedy without Claude choosing the action.
- The operation executes through scheduled platform workers.
- The result is verified automatically.
- The recovered item advances to the next eligible stage.
- Successful and unsuccessful remedy outcomes are retained for future decisions.

The platform must also demonstrate safe refusal to repeat a remedy that cannot work.
