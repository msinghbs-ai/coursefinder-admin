# Searchable Admin pages (s1270)

Platform Admin request relayed by SS-Programme-Control, 26 Nov 2026 17:47. Lane: S1-API-Frontend-Delivery. Pilot #1676. Frontend only: no migration, no new setting, no backend read, no Consumer API (G3) change, spend US$0. Kept separate from the PIM go-live blockers.

## What it does

A search bar sits at the top of eight long Admin pages and stays in view under the page header while the page scrolls.

| Page | Route |
|---|---|
| Layer 2/3 Build & enrich (Operations, Data Delivery, Autonomous PIM) | `#layer-2-discovery` |
| Settings | `#environment` |
| Models & services | `#services` |
| Layer 1 | `#layer1` |
| Coverage | `#coverage` |
| Platform health | `#health` |
| Scheduled jobs | `#jobs` |
| Go-live checklist | `#migration` |

The list is `SEARCH_PAGES` in `src/nav-map.js`. Adding a page is one word in that list.

1. A person types a name, a setting label, a setting key, what uses a setting, or a plain word that means the same (cap or limit, retry or re-read, stalled or stuck, website or Zoho).
2. Results show the kind (Tab, Section, View, Setting), the label, the key where there is one, and where it sits (for example `Settings › Pipeline steps › Onboarding`).
3. Choosing a result (click, tap, or arrow keys and Enter) opens the tab, the Data Delivery view, the card or the fold that holds it, scrolls it clear of the sticky bar, highlights it for a few seconds and moves keyboard focus to it. Press `/` to jump to the bar and Escape to clear it.

## How it is built (reuse, no parallel structure)

| Part | Where | Notes |
|---|---|---|
| Bar, results, jump | `src/PageSearch.jsx`, `src/page-search.css` | One component. `PageLayout` draws it when a page opts in, so it uses the existing tabs and the existing route (`navigate`). |
| Matching | `src/lib/page-search.js` | Pure functions: word and synonym matching, every word must be found, label first. The synonym sets are interface vocabulary, not data (s930 does not apply to them). |
| Tabs | `shownTabs(page, rank, active)` | The same role-filtered list the page itself draws, plus a `find` keyword string per tab in `nav-map.js`. |
| Sections and controls on the open tab | DOM scan | Cards, folds, headings and `[data-setting]` rows that the page has drawn. |
| Settings | `SettingsRegister.jsx` registers entries | Every setting and group from the `admin_settings_register_read` result the screen already holds. A jump opens the Advanced System Keys drawer, the group tab, the card, and focuses the field. |
| Data Delivery and PIM | `PimDelivery.jsx` registers entries | The three PIM views and their sections; a view is local state, so closed views are reachable only through registered entries. |

## Role permissions

The bar offers nothing the role was not given. Tabs come from the role-filtered tab list. Setting entries come from the settings read the signed-in role already received. A page the role cannot open redirects as before and draws no bar. Tests: a Pipeline Operator is not offered the Adapter builder tab (minimum rank 5) and a Data Manager is; a Counsellor is taken to Courses and sees no bar.

## Limits to know

- It finds controls inside a closed card or fold, or on another tab, only where the screen registers them (Settings, Data Delivery and PIM do). A control elsewhere is found once its tab is open; a tab result reaches that tab and the person searches again. Screens can register entries with `usePageSearchEntries` in one place without changing the component.
- It never changes a setting, and it adds no backend read, so it carries no cost or load.
