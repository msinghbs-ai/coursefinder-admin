## Context and execution budget (Platform Admin, 10 November 2026)

**Reason:** Claude/ChatGPT use is subject to weekly usage limits. Repeating discovery, loading full historical registers, re-querying the whole database or repeatedly running a full test suite wastes limited agent time and delays production data delivery. **The Admin repo is the durable memory, not the chat.** This section is a binding work method, not a new task queue.

**At the beginning of any session or scheduled development run:**
1. Read this operating model (once for the session), the **top Quick Start block** of `docs/platform/nz-enrichment-brief/INDEX.md`, and the *specific* F-domain/substep in `STUDYSEARCH-FEATURE-ACCEPTANCE.md`. Obtain current task status from the **most recent matching entry** of the existing Execution Register or its current derived Programme Status; use GitHub search / file ranges rather than loading the complete register. Read only the affected implementation files and PR. Historical dated narratives are evidence, not instructions to repeat obsolete discovery.
2. Identify the **one next executable subtask**: ID, known completed work, exact unresolved blocker, relevant existing code path, expected data gain, acceptance proof and smallest needed change. If a user has supplied a current observation, use it as a dated baseline without immediately checking every production table again. New work starts by reconciling *material deltas*, not resurveying the platform.
3. **Evidence reuse first:** rely on already recorded schema inventories, last successful test evidence, latest PR CI, function checksums and prior read-only query results until a particular decision or release depends on fresh truth. For each additional tool call, be able to state which *specific unresolved question* it answers. Do not perform full-schema inventories, whole-platform status polls or generic multi-domain SQL queries for a single bounded slice.
4. **Targeted testing while developing:** use the smallest affected tests/fixtures to prove a change; do not run the entire suite during discovery, for every exploratory change or independently in every agent. At the integration/release boundary perform the mandatory full green, zero-skipped governed CI suite, production-parity checks, before/after md5 guards, independent QA where applicable and live outcome validation. Reuse exact-head CI evidence; rerun the suite only when the head changes or its prior evidence is invalidated. Never sacrifice a genuine G1–G4 or production safety gate to save usage.
5. **Bounded parallelism:** delegate independent code areas only when that creates a measurable speed gain. One owner per file/function/migration, one integrator, no duplicate agents exploring the same question. Discovery is a *short gap check* with an explicit stop condition; when the architecture or path is already known, implement the next action immediately. A pilot, new report, framework, controller, dashboard or task plan is never a prerequisite unless it fills a demonstrated capability gap.
6. **No chatter as a work product:** short progress reports only at material milestones (actual data gain, code qualified and released, verified new blocker). Put the detailed technical evidence and next executable substep in the **existing** Execution Register, update the INDEX Quick Start pointer and derived Programme Status when materially changed. On resumption, consume those small pointers instead of rereading chat transcripts. A green job with zero new admission is reported accurately, not counted as completion.

**Usage discipline:** default to one focused repository/context pass, one limited live evidence pass only where necessary, targeted development tests, and one release acceptance pass. Additional calls must be justified by a concrete discrepancy, a changed code head, safety-critical release condition or an independent-validation finding. There is no fixed query/test ceiling that overrides mandatory release controls.

**Completion proof:** preserve a clear evidence chain of `F-domain.substep → IQ/SS issue → PR/commit → deployed function/job/settings → actual source-backed admission → consumer publication/verification`. If the last stages have no gain or a valid hold, leave the substep open with exact cause and next retry; **do not restart discovery**.

## Approval requests must be actionable and UI-verified (Platform Admin, 10 November 2026)

**Never ask the Platform Admin to “approve”, “switch on”, “open Settings” or “run the UI control” without verifying the actual route and whether a NEW human decision is required.** A database approval row, migration gate, technical permission and business/policy authorisation are different things. The presence of `approval_status` or a service-only function does not by itself constitute an unmade Platform Admin decision.

Before escalating:
1. **Reuse previous authority:** search only the relevant current decision/PR/approval package. Determine whether the exact scope is already approved. Do not request the same authorisation a second time. Separate an approved decision not yet implemented from a new decision outside scope.
2. **Validate the actual control:** inspect the current deployed Admin route, rendered component, role rank, underlying RPC/write function, settings row and required audit reason; when appropriate, verify in the actual signed-in UI, not just a design document or stale screenshot. Never invent menu labels, buttons, a route or a control.
3. **Provide a complete actionable request** only for a genuinely required human action, containing: (a) why the action requires a human and why no recorded approval covers it; (b) exact object(s), IDs, counts, audience/consumer scope, old → new value and operational effect; (c) an actual clickable UI path and step-by-step instructions with verified access/role, or an explicit **“No Admin UI control exists”** statement and a prepared reviewed migration/authorised workflow, with code/PR path and required approver; (d) precise audit reason/text; (e) preconditions, safety and financial impact, rollback/forward recovery; (f) how the system will confirm the result. Ask one precise decision, not a vague "approval?".
4. **If the UI does not exist:** Do not redirect the Platform Admin to a fictional screen, ask them to manufacture an approval row, or propose raw production SQL as an ordinary substitute. Claude must own the technical implementation and supply the reviewed, authorised release workflow. A service-only write route is **not a UI action**. Where the mechanism embodies an explicit human approval policy, preserve it; propose a separately approved policy/profile change with exact scope rather than silently inserting approvals.
5. **No avoidable handback:** technical gates and the mechanics of implementing a scoped decision already approved belong to Claude through the existing CI/QA/migration/release process. Do not escalate a database row or old `pilot` label as a fresh human-policy decision without checking the actual controlling rule and recorded scope. Park only the protected action if a genuine new authorisation is needed; progress other critical-path work.
6. **Keep records brief:** write the approval evidence and exact instructions under the existing F-subtask and register; do not create a new approvals dashboard or a long repeat audit. If an actual control is missing, record it as an operator-UI acceptance gap under F-OPS.04.

**Example boundary (10 Nov R23/R24/course publication):** the earlier 10-course publication verification authorisation is scoped, not a blanket all-course go-live. The technical `publishing.publication_approvals` rows are a prerequisite enforced by a service-only function and historical controlled UAT profile; they are **not themselves a request for the Platform Admin to click a non-existent button**. The engineer must explain whether its proposed migration fits the existing bounded authorisation and the profile's true human approval semantics; any genuinely new publication-policy authority must be presented explicitly with actionable instructions. Never infer that a "pilot" profile is authorised to publish the full catalogue.

Do not stop a separate module's work without its owner or silently take ownership of another module's queue. Cross-module findings go to that module's existing F-subtask/IQ and a concise handoff, not a new investigation or duplicate PR.

1. **Developer requests are product acceptance, not chat notes.** Keep `docs/integrations/WEBSITE-DEVELOPER-REQUIREMENTS.md` the one canonical Wix/Zoho request register, with original requester/date and stable R/O/Z plus REQ IDs from the dated cross-reference. A module implementing a request maintains field-by-field status: official source → canonical schema/value → validation/admission → Website API v3 → Zoho API v3 → actual Admin UI column/filter/record detail → verified consumer response → communicated status. Do not count a field as delivered because it is only in a document, JSON schema, migration or one consumer. Keep recorded partial/unknown conditions truthful and timestamped.
2. **New field design includes database and UI in the same implementation.** First verify the existing canonical tables, lineage, source evidence and consumer payloads. Add a typed/effective-dated value or additive table **only if** present objects cannot represent the provider/course/campus/intake/edition grain and its evidence. Record identity and published source date/time zone; never invent dates, extrapolate academic-calendar dates to unproved course offerings, use a provider headquarters as course campus, or treat an admission-requirements table as intake evidence. Source discovery success, green jobs and AER admissions are not F-INT delivery.
5. **On demand is deliberate, not an endless standing queue.** For an explicitly requested Run Now, apply v1.17's scoped `security.on_demand_open_v1`/`on_demand_close_v1` and bypass scheduled toolset shares/cadence only within that request; preserve account credit reserve, safety/identity, spending evidence and publication authority. Do not create a new request or restart paused work because a handoff or mandate document was updated. Ownership of an open request remains with its initiating operator/session until explicitly transferred; close it after its in-flight work settles, with measured credits and outcome. An expiry is not proof of successful close.
6. **Website/Zoho v3 and freezes.** Website API v2 and Zoho v2 remain unchanged. Website v3 pre-go-live additions follow Decision 277; the Zoho v3 implementation must be built against the actual current v3 contract, not an outdated draft, and each consumer must be tested independently. New fields (including optional intake/deadline evidence and reason codes) need typed/null semantics, stable enum, pagination/sync parity and consumer-facing documentation. Developer notification and the current consumer API merge/freeze rules remain intact. Do not claim Zoho v3 is live unless its deployed route has been verified.
7. **F-INT outcome measurement.** Record dated denominators for active eligible courses, courses with an intake, intake rows with year, exact start date, and application deadline, plus month-only, rolling, held, no-official-calendar and never-read reasons; net newly retained valid rows (and corrected/withdrawn wrong dates), actual Website v3 / Zoho v3 read-back or explicit unknown, spend and cost per admissible result. UI is accepted only when a signed-in operator can filter to the missing rows and see source, next retry and the actual result. Use the existing `STUDYSEARCH-FEATURE-ACCEPTANCE.md` F-INT record and Execution Register; no extra tracker.

**This standing rule does not authorise a new vendor budget, inferred academic dates, protective policy changes, consumer cutover or bypassing G1–G4.** Release and report only evidence-backed F-INT progress. When an AER session reports 43 admitted courses/105 entry rows, retain that under F-AER; it is **not** an intake gain.

2. **Long-page failures are a technical recovery lane:** when AI responses truncate at a token cap or return no answer for a long official page, reuse the existing stored evidence and split into deterministic, source-identified award/terms sections for bounded AI extraction. Judge success by newly accepted canonical facts and consumer parity, not by requeued reads.
3. **Readmission is not a blank approval:** `sch_elig.readmit_on` is a gated restoration mechanism for an earlier **machine withdrawal** only after the exact award's own official source newly satisfies the current evidence-safe rule. Confirm historical withdrawal actor/reason, current identity, edition, exact eligibility quote, unaffected manual rejection/lock, source consistency, idempotency and unchanged course-link authority before any activation. Restore the **same** canonical record as unpublished; normal publishing rechecks eligibility and evidence. A how-to-apply page, several-awards directory or mixed/ambiguous audience must not reactivate a record. Use existing scope-controlled authorisation and an exact first-cycle verification; if the change has a new protected policy effect, request **one actionable** Platform Admin decision as required by the Operating Model. A green PR alone does not activate the gate.
4. **No false success:** a live reader with 9 correctly domestic-only, 6 refused, 0 new admissions is valid safety evidence but **not a scholarship admission gain**. Count published scholarships, active canonical awards, new descriptions, application method, duration, nationality, benefit detail, verified course links and withdrawal/re-admission separately. Avoid equating "1,578 of 1,655 detail reads" to 1,578 complete profiles; quantify per-field usability on the **published denominator** and newly admitted values.
5. **Developer v3 and operator UI in the same feature:** maintain the single `docs/integrations/WEBSITE-DEVELOPER-REQUIREMENTS.md` register and `api-v3/API-V3-FIELD-DEFINITION.md` for S2-Scholarship. Any new field or filter requires clear types, source and null semantics, signed-in **existing Scholarships Catalogue/Detail and Layer 2/3 Data Delivery** column/filter/drill-down, and real Website/Zoho read-back. Optional columns and facets; no new dashboard or 35-setting control panel. Preserve v2 freeze, v3 pre-go-live/communication rules and separate consumer contract ownership.
6. **Self-sustaining use, bounded cost:** use existing scheduled reading/recheck/settlement and authorised on-demand pathway for explicit immediate requests only. Keep vendor-account credit floors, source/manual safeguards, traceable AI spend, lease expiry and idempotent recovery. Distinct country scholarship structures should be handled through versioned source-grounded prompts and shared claim schemas with qualified regression fixtures—not country-by-country hard-coded admission patches or unauthorised autonomous policy edits.

**F-SCH acceptance:** two unattended cycles with actual retained field and valid admission/publication gains or proven terminal no-evidence outcomes; one independently checked current-source positive and negative case (including withdrawn and restored), a released long-page recovery that clears the known technical blocker, verified Website v3 and Zoho v3 status, and actionable existing Admin UI coverage filters. Use the F-SCH acceptance rows and original register, not a new roadmap. This section is governance and does **not itself** toggle `sch_elig.readmit_on`, change spend or authorise a consumer cutover.

## Root-cause-first delivery and PR containment (Platform Admin, 10 November 2026)

**Permanent engineering rule:** A stream of small defect patches, PRs, repeated QA loops or status messages is **not** an acceptable substitute for closing the underlying feature's end-to-end acceptance. Use the existing F-subtask and IQ/SS issue to own a complete operational result. This applies to all development and future sessions; do not wait for a new chat prompt after each QA finding.

1. **Fix at the owning layer:** For every blocking QA defect, identify the failed invariant, producer/consumer contract or reusable source of truth. Correct the owning function, state model, shared validator or transaction boundary rather than adding a caller-specific workaround, ad-hoc exception, duplicate switch, temporary hold or another branch merely to cover the symptom. Prove with a focused regression that fails against the old implementation and passes after the fix. Preserve source identity, evidence, manual locks, human/machine actor separation, idempotency, consumer G3, budgets and authorisation.
2. **Prevent recurrence:** If a defect class recurs in the same feature or across two adjacent PRs (identity conflict, queue race, mismatched actor status, absent flag propagation, stale signature, premature publication), **stop the patch chain**, inspect the shared root cause and correct every affected caller/state transition together. Reconcile all known QA findings at the current head; do not knowingly ship a structurally related 'low severity' defect that undermines identity, integrity or safe admission. Record any consciously deferred non-blocking issue with owner, evidence and explicit acceptance boundary.
3. **Bound the PR graph:** Prefer one self-contained, independently testable slice per F-subtask. Sequence genuine dependencies, combine tightly coupled adjustments where safer, and retire superseded drafts. Avoid fragmenting a single feature into multiple PRs solely to generate progress. Rebase/merge current main once for the final qualified head, regenerate the governed test register if required, then run the necessary exact-head QA and CI. Do not repeatedly trigger full CI during drafting; don't skip mandatory final release gates. One production release at a time.
4. **Functional acceptance, not patches:** A PR is complete only when its intended Admin action, real source→validate→admit→publish route and exception/retry transitions are verified where relevant. 'UI button exists', 'setting enabled', 'QA green', 'migration merged', 'task created' and 'work pending' are intermediate states, not acceptance. Run the operator journey end to end, especially for on-demand Fill fields, basic→enriched descriptions, AI course admission and consumer read-back.
5. **Cost and control discipline:** Before adding a setting, queue, fallback, job, panel, new schema or scheduling rule, show why an existing approved component cannot serve it. Classify every introduced setting as human-operated, automatic/internal or temporary; avoid defaulting technical experiments into the human Settings UI. Retire obsolete internal paths with dependency checks and usual housekeeping; a setting read by deployed code need not be displayed or managed by a human.
6. **Handover that prevents re-discovery:** Update the **existing** subtask status and short Admin Quick Start only on material change: root cause, integrated fix, remaining acceptance evidence, blocker, next executable action. Reuse the existing execution register for technical audit. Stop repeating QA/CI 'still running' messages or requesting confirmation for ordinary engineering judgement. Do not create another mandate, status document or tracker for each correction.

**QA failure means repair the owned feature, not re-plan the programme.** If actual permissions, protected consumer/deletion approval or finances block one operation, record the exact gate once and continue unrelated authorised work. This rule does not loosen mandatory independent QA, CI, migration safeguards or production approval checks.

## Test-run efficiency: one full run per final head, fast by design (Platform Admin, 10 November 2026; permanent decision)

**Why:** The governed full suite is the release gate, but a recent run takes 10 to 15 minutes (all specs run one after another on one runner) and a failed run costs the same again. In practice the hours are lost to repeated full runs, not to one run: fix, rerun, fail, fix again; a generated-file conflict that forces a merge and a new run; and several independent releases each paying for their own run. This rule removes the waste. It does not remove or weaken the gate.

1. **Targeted tests while developing; one full run on the final head.** During development and QA, run only the specs the change touches plus the central guards (G2 `s32`, G3 `s57`, housekeeping `s42`, test governance `s120`, and the release contract `m245`/`s70`) and any fixture the change owns. Keep PRs as drafts until the final head is qualified, because a draft gets the lightweight path and does not start the full suite. Mark ready for review once, at the final head. Do not push cosmetic or documentation-only follow-ups to a head that has already passed, because each push starts a new full run unless the reuse rule applies.
2. **Fail early and read the cause first.** When a full run fails, read its failing specs and the cause before pushing any fix, repair the owning function (Operating Model v1.6 rule 1) and prove the fix with the failing spec alone. Do not rerun the full suite to find out what failed. Do not push a fix, then another, to a head that is in a full run.
3. **Do not pay twice for the same evidence.** The evidence-reuse rule (full-suite result reused when the dependency fingerprint is unchanged: release notes, changelog and docs only) stays. Never push to a PR head only to resolve a generated-file conflict until the PR is otherwise final. Resolve the conflict once, at the final head, by regenerating the file (`node scripts/test-register.mjs > docs/platform/TEST-REGISTER.md`), never by editing it by hand.
4. **Batch independent releases through one full run.** When two or more reviewed, independently QA-passed slices are ready at the same time, merge them into one integration branch (one full run, one deploy, one production verification) rather than running one full run each. Each slice keeps its own migration guards and its own forward-recovery file, and each slice's verification is reported separately. Do not batch a slice that failed or is awaiting QA, a protected consumer (G3) change, or work that needs a different production approval. Batching is for speed, never to hide a failing slice. The one-release-at-a-time rule still applies to production mutation: apply and verify in dependency order.
5. **Faster full runs (CI engineering, not policy).** The full suite is split into parallel shards and the results are merged back into the single evidence bundle and the single required check, with npm and browser downloads cached. Test content, the `@deployed`, `@responsive` and `@live-acting` rules, the evidence bundle and the check name do not change. Status: in progress under Admin Quick Start P0; the full run keeps its current speed until the Pilot change is merged and measured.
6. **Generated register, no conflict reruns (target).** The target is for the test register to be generated and verified by CI from the same run, so that a PR no longer carries a conflicting generated file. This changes the G4 "register regenerated in the same change" rule in the Pilot `CLAUDE.md` and `tests/uat/cf-247-s120-test-governance-contract.spec.mjs`, so it takes effect only when those are changed and merged by a reviewed Pilot PR. Until then the existing G4 rule applies, with rule 3 above.
7. **Measure it.** Record the full-run wall-clock time, the number of full runs per release and the number of reruns caused by failures or conflicts in the Monday line. The aim is one full run per final head, and a wall-clock time measured in minutes.

**What does not change:** the mandatory independent QA, exact-head CI before merge, migration safeguards, consumer API (G3) approvals, financial limits, manual locks and production verification. Targeted tests are never a substitute for the full run before merge; they are what is run before it.

## Bounded work on worker write paths; throughput is measured, not assumed (Platform Admin, 10 November 2026; permanent rule)

**Why:** On 10 Nov the course-description cap went from 500 to 2,000 readings a day and real output fell to about 118. The AI worker records up to 40 answers in one API call (8 s statement time-out); a trigger ran the full machine admission (catalogue scans and a Website read-back, about 1 s a reading) inside that call, a time-out cancelled the whole batch, and 385 paid answers were lost. A deadlocked standing job also left 1,500 items queued with no runner. Evidence: [execution register, 10 Nov 23:55](STUDYSEARCH-EXECUTION-REGISTER.md).

1. **A worker or API write path does bounded work per item.** An RPC called by a worker (`svc_*` recording calls) and every trigger it fires do constant-time work per item: validate, record, enqueue. Admission decisions, catalogue-wide scans, consumer read-backs and anything whose cost grows with data volume belong to the catalogued job that already settles that state, never inside the API statement (`authenticator`: `statement_timeout` 8 s, `lock_timeout` 8 s). Before adding work to a trigger or RPC, name the slowest call it makes and its cost at current volume.
2. **A swallow block is not a time-out guard.** `exception when others` does not catch `query_canceled` (a statement time-out or a cancel): the whole statement, and every item batched in it, is lost. Never describe a path as "never fails" because of such a block; bound the work instead (rule 1).
3. **A capacity change is verified by measured throughput.** Raising a cap, batch size or daily allowance is an intermediate state, not delivery (v1.5 rule 3). At the next cycle, measure attempted against recorded against failed items, worker batch errors and statement time-outs in the logs, and report that, not the setting. A raised cap that lowers real output is a P1 defect.
4. **No orphaned work after a job fails.** A terminal job failure (deadlock, time-out) must not leave its items queued or leased with no runner. They are settled, released to the next job or raised as an integration issue in the same cycle, never left silent.
5. **Paid answers are recovered before re-asking.** An AI answer already received and stored is replayed through the recording route before the item is asked again (the existing replay), consistent with the cost discipline above.
