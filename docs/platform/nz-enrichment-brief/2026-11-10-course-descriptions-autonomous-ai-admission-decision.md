# StudySearch — Platform Admin decision: autonomous AI course descriptions from stored course pages

**Date:** 10 November 2026, Australia/Melbourne.
**Owner:** Claude, sole accountable engineering and Integration Controller (Operating Model v1.1).
**Priority:** P0 delivery for F-CDESC and F-OPS; no new university pilot.

## Platform Admin's explicit direction
“Course description is AI; there cannot be any confusion about it, either it is or not and keep moving to fill them.” Together with the immediately preceding instruction: reuse existing stored course pages and start filling all courses without a new provider-style pilot.

**Decision:** AI is the intended production generator for course descriptions. Develop and deploy a **distinct, narrow, source-verified automatic machine-admission route** for courses whose descriptions pass objective identity, official-page/evidence, sentence quote, factuality, duplication, manual-lock and rejection-memory checks. This supersedes the 3 November D5 requirement to keep every first course-description admission waiting for an individual human Layer 4 decision, **only for that newly implemented safe class**. Existing exceptions, ambiguous claims, missing/incorrect course pages, unsupported text, rejected values and locked fields remain held for a person or an evidence-triggered retry. No fake human approval, mass-clicking Layer 4, bulk UPDATE of `catalogue.courses.description`, or unreviewed settings shortcut. Reconcile and settle current Layer 4 work with an explicit machine actor and audit/provenance only where the new route qualifies.

The change to the admission policy is **authorised to be implemented**. It does not assert that the currently installed code already supports machine admission for course descriptions, and it does not authorise bypassing technical deployment gates, permissions, G3, spending ceilings or source checks. The old setting `enrich.course_description_review_first=100000` is a deliberate manual-review barrier; **do not lower it to impersonate a human trust sample**. Instead add a narrowly scoped, independently QA'd and audited machine decision route with a setting that ships off until the feature is demonstrably ready for a governed controlled activation.

## Implementation contract
1. **Census all active eligible AU/NZ/CA courses** with authoritative course+provider identity, published/lifecycle state, correct course page/evidence hash and freshness, existing description, manually locked/rejected cases and next revisit. Separate verified stored course pages, source-missing, identity ambiguous, source-gone, held/review and legitimately month-only or no-descriptive-content; avoid pretending a `bound` status proves HTML is stored.
2. **Existing source-first reader:** reuse stored, identity-proved official *course-specific* pages before direct official-page acquisition and budgeted Firecrawl. Select correct page for the exact course/provider, programme type and variant; never use a generic university About page, page metadata or another course as proof of course-specific claims. A provider profile is not a course description.
3. **AI generation:** produce a clear, useful, distinctive course description (typically 1–4 sentences) describing verified course scope, what students study and, only if directly supported, specialisations, modes, practical/research components and relevant pathways. Every factual sentence has an exact quotation or deterministic structured official fact, source URL/evidence ID, content hash, model/prompt/version, course ID and captured timestamp. No unsupported price, accreditation, ranking, employment, guaranteed outcomes, duration, campus, intake or visa assertions. Never auto-cut or paraphrase a statement in a way that breaks its supporting quotation.
4. **Machine admission:** a new explicit audited course-description safe-class admission rule (not a simulation of Layer 4 human approval) rechecks identity, source, provenance and every sentence at write time, prevents stale/duplicate/cross-course writes, preserves manual edits, locks, previous rejections and source lifecycle and records before/after/recovery. For existing Layer 4 proposals, use the same reviewed safe-class rule and machine settlement ledger, preserving human history. Content failing the safe rule stays genuinely held, with exact next action, and other courses continue.
5. **Throughput:** remove permanent 10/20-university pilots. Use fair bounded queues and configurable G2 scheduling across all eligible courses; classify the bottleneck as source unavailable, reader timeout, AI budget, validation, human exception, source freshness or publication lag. Prefer stored pages and existing AI budget. Calculate productive eligible→read→pass→admit→Website/Zoho conversion and run until the eligible backlog is drained or given durable actionable holds. A small technical canary is permitted inside QA, not as a new programmatically enforced pilot phase or an approval ceremony.
6. **UI and on-demand:** inside existing Course Catalogue and Course Detail, provide `Fill description` / `Recheck description` using existing Enrich fields, job queue and governed Run Now/Verify; one course, selected courses and a selected-provider scope, with bounded preview/selection and reason, without an alternative scheduler. Show Missing / Source-ready / AI-read / Held / Machine-admitted / Human decision / Website feed / Zoho feed / Verified HTTP distinct; last attempt, next retry, source URL, evidence and actual gain. Reuse the P0 Data Delivery scorecard at Layer 2/3 → Operations (F-OPS.03A).
7. **Provider-description Run Now gap:** `run_now.jobs` was observed to hold only `["intake-dates-apply"]` on 10 Nov; `provider-description-read` is already catalogued at rank 6 and the Provider Description Run & Validate screen exists. The 5 Nov 20:03 Platform Admin post-deploy activation decision is existing authority. The signed-in authorised Admin route must add `provider-description-read` to the existing list with an audit reason after verifying job, roles, switches and safe cohort contract. Do not overwrite other list entries, bypass the UI permission, or claim Run Now works until a live action completes with saved cohort IDs, actual outcomes and publication read-back. Add direct Provider Catalogue entry-point using the same governed cohort, not a direct SQL fill.
8. **Validation & acceptance:** full current CI and isolated production-shaped SQL fixtures; negative tests for incorrect page, different campus/course, obsolete page, unsupported claim, same-evidence retry, already rejected/manual value, empty answer, excessive similarity, timeout, cost cap and consumer lag. First **actual new** canonical course description after authorised release plus correct Website/Zoho source/HTTP where supported; further admissions across more than one provider after at least two unattended runs; exact 24-hour/7-day net gain in existing Admin UI with observed timestamps; no false published count from green cron, proposal or Layer 4 queue.
9. **Existing acceptance record:** update F-CDESC.01–.05 and the sole execution register; no second tracker, duplicate UI or new long-form governance plan. Claude owns integration, QA, release sequence, recovery and progress; escalate only protected financial/destructive/G3 permissions outside previously recorded authority.

**Non-acceptance conditions:** “AI is making proposals”, a green worker, an added PR, a 20-course sample, or 163 unchanged descriptions do not constitute delivery. Success is a durable and growing count of evidence-backed **canonical and correctly consumer-published course descriptions**, with honest exceptions and autonomous continued execution.
