`consumer_api_check_v1`'s comparison was reproduced as one `SELECT`, with no flag or event writes.

- **Function check.** For each function in `pipeline.consumer_api_baseline`, the live `md5(pg_get_functiondef)` from `consumer_api_functions_v1()` must equal the baseline md5. Missing and changed functions are reported.
- **Relation check.** For each baseline relation, every baseline column must exist with the same type: from `consumer_api_relations_v1()`, or directly from `pg_attribute` when no function names it any more.
- **Added functions.** Any consumer function not in the baseline is reported.

The comparison was run with `search_path` set to empty for that one transaction, as `consumer_api_check_v1` runs (`SET search_path TO ''`).

**Method note.** A first run under the MCP session's default `search_path` (`"\$user", public, extensions`) reported three `api` functions as changed: `api.query_embedding_cache_get`, `api.query_embedding_cache_put` and `api.vector_candidates`. That was an artefact. `pg_get_functiondef` prints the `extensions.vector` type unqualified when `extensions` is on the path, so the md5s differ from the baseline taken under an empty path. Under the empty path the guard uses, there is no drift. The session's path was reset afterwards and confirmed back to the default. Lesson recorded in the parity tool: every manifest records the `search_path` its md5s were taken under, and the fixture sets the same path.
